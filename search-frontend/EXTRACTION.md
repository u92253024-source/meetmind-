# 資料抽取方法論 — 從 98 份 PDF 到 983 筆結構化提案

本文件說明 `data.json` 的產製流程：使用什麼工具、怎麼切分會議紀錄、
如何判斷「本次提案」與「前次執行情形回顧」、去重邏輯的設計與已知限制，
以及本次（2026-08-11）獨立品質驗證發現的問題。

這份文件補的是 [REPORT.md](REPORT.md) 第 3.18 節指出的缺口——
原專案沒有留下任何說明「PDF 如何變成 JSON」的紀錄，而這正是整個作品技術含量最高的部分。

---

## 一、抽取工具

資料並非由本次的 `index.html`／`indextest.html` 這兩支純前端程式產生。
它們是**消費端**（讀 `data.json` 做搜尋），真正的**產製端**是另一個獨立專案：
一個以 **React 19 + TypeScript + Vite** 開發、整合 **Google Gemini（`@google/genai`，Gemini Flash 模型）**
與 **Firebase（Authentication + Cloud Firestore）** 的 PDF 結構化擷取工具。

| 項目 | 內容 |
|------|------|
| 前端框架 | React 19 + TypeScript + Vite |
| AI 模型 | Google Gemini（Flash 模型），透過 `@google/genai` SDK 呼叫 |
| 雲端同步 | Firebase Authentication（Google 帳號登入）＋ Cloud Firestore |
| 輸出格式 | 一鍵匯出為標準 JSON，即本專案使用的 `data.json` |

## 二、兩階段擷取邏輯

### 階段一：定位會議討論區段

對每份 PDF 全文，先找出「會議討論內容」的起訖範圍，排除議程封面、簽到單、附件等無關內容：

- **起點關鍵字**：報告案、討論事項、討論案由、討論提案、討論議案、討論項目、提案討論
- **終點關鍵字**：散會、會議結束、閉會

### 階段二：欄位結構化

在鎖定的區段內，把每一個提案解析為 `data.json` 的標準欄位：

| 欄位 | 內容 |
|------|------|
| `meetingName` | 會議完整名稱（如「國立政治大學 100 學年度第 2 學期第 2 次教務會議」） |
| `title` | 提案標題（如「【提案一】案由：…」） |
| `unit` | 提案單位（如「教務處註冊組」） |
| `content` | 提案說明與內容 |
| `result` | 決議結果（如「照案通過」「修正後通過」） |
| `fileName` | 來源 PDF 檔名 |
| `page` | 提案在 PDF 中首次出現的頁碼 |
| `id` | 9 碼隨機英數字，逐筆生成的唯一識別碼 |

**如何判斷「本次提案」而非「前次會議執行情形回顧」**：
會議紀錄開頭通常先條列前次會議各案的「執行情形」，才進入本次討論事項。
階段一鎖定討論區段的起點關鍵字（報告案／討論事項／討論提案…）本身就把回顧段落排除在擷取範圍之外，
這也是本次獨立驗證（見下方 2.2 節交叉比對）確認 999 筆與 PDF 中 1,851 個「案由：」之間差額的成因。

## 三、去重邏輯與已知限制

原工具採**雙鍵比對**：以「會議名稱 ＋ 提案標題」是否相同判斷是否為重複紀錄。
跨學年度出現同名提案時（例如不同年度都有「修正課程實施辦法」），
系統會賦予各自獨立的 `id`，並在標題前加註 `[學年度]` 前綴以利辨識，確保歷史提案不被覆蓋。

**已知限制（本次驗證發現）**：雙鍵比對抓的是**完全相同的標題字串**，遇到標題被重新措辭時會失效。
`95-3.pdf` 與 `95-臨時.pdf` 就是這種情況——兩份檔案記錄同一場會議的同 16 個提案，
但 `95-臨時.pdf` 把每個標題改寫成「討論完成案件提案 N」「臨時會議討論提案 N」，
與 `95-3.pdf` 的「提案 N」字串不同，雙鍵比對因此判定為不重複，讓 16 筆重複紀錄漏網。
這批漏網重複已於 2026-08-11 以人工逐筆比對決議欄位的方式抓出並修復（詳見 [REPORT.md](REPORT.md) 3.2 節）。

**跨年度重複機制運作正確的案例**：搜尋「性別研究學程」目前仍會出現 2 筆，
分別是 95-2.pdf（【臨時動議案一】，決議「延至下次會議討論」）與 95-3.pdf（【提案三】，正式決議定案）。
這不是重複，是同一提案在兩場真實會議中的合法歷程——原工具的雙鍵比對（標題不同：
「臨時動議案一」vs「提案三」）與跨年度前綴機制在這裡的判斷是正確的，本次驗證予以保留。

## 四、本次（2026-08-11）獨立品質驗證

在原工具的自動化擷取與人工審閱之外，這次針對 `data.json` 做了一輪獨立的資料品質稽核，方法與發現如下：

| 驗證項目 | 方法 | 結果 |
|----------|------|------|
| 欄位完整性 | 999／983 筆全量統計 8 個欄位是否有空值 | 零空值 |
| ID 唯一性 | 全量比對 `id` 欄位 | 零重複 |
| PDF 連結正確性 | 98 個 `fileName` 參照與磁碟檔案逐一比對（含大小寫） | 100% 對應，零死鏈 |
| 抽取完整性 | 98 份 PDF 以 pypdf 全文抽取，統計「案由：」與提案編號出現次數，與收錄筆數交叉比對 | PDF 中 1,851 個「案由：」正確收斂為 999 筆不重複提案 |
| 抽取正確性 | `105-1`、`99-2`、`113-1`、`95-3` 四份逐案人工核對 | 「前次會議執行情形」回顧段落均正確排除，無漏收 |
| 重複資料 | 依「會議名稱＋正規化案由」計數，逐筆比對決議欄位內容 | 找出 `95-3.pdf`／`95-臨時.pdf` 16 筆漏網重複（見上方三、） |
| 個資風險 | 以「學號」「○○同學」「9 碼數字」等樣式全量掃描 | 找出 9 筆未遮罩的學生姓名／學號，已完成遮罩 |
| 搜尋行為 | 以 Python 重現前端 `searchText` 組成與比對邏輯 | 找出多關鍵字查詢失效問題，已修復 |

修復後的最終狀態：**983 筆**，8 欄位零空值，ID 零重複，PDF 連結零死鏈，
姓名／學號全量掃描零殘留，39 項自動化回歸測試（多關鍵字搜尋、相關度排序、XSS 逸出）全數通過。

## 五、給評審／後續維護者的重點摘要

如果只能記住三件事：

1. **抽取工具是 Gemini Flash 模型驅動的兩階段解析**（定位討論區段 → 欄位結構化），
   不是本次修改的 `index.html`／`indextest.html`——這兩支是純前端搜尋介面，只消費 JSON，不做抽取。
2. **原工具的雙鍵去重（會議名稱＋標題）在標題被改寫時會失效**，這是本次抓到的唯一系統性遺漏，
   已用「決議內容比對」的方式補強驗證並修復。
3. **不是每個「同標題出現兩次」都是錯誤**——同一提案跨會議延議再決議是正常現象，
   驗證時務必先看決議內容是否為前一筆的精簡改寫，而非只看標題是否相似。
