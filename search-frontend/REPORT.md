## 一、總體評價

這是一個**資料價值遠大於程式複雜度**的作品，而這正好是它的優點。

23 個學年度、102 場會議、983 筆提案（2026-08-11 去重後）的結構化語料，是無法用任何公開資料集替代的機構知識。
程式端刻意維持零框架、零後端、單一 HTML 檔案，讓一個沒有資訊人力的行政單位真的能長期維護下去——
這個取捨是對的，不是能力不足。

真正需要在參賽前處理的，是四件事：**個資遮罩、資料去重、多關鍵字搜尋、AI 抽取過程的呈現**。
（個資遮罩與多關鍵字搜尋已於 2026-08-11 完成修復，詳見 3.1、3.5、3.12。）

## 二、亮點

### 2.1 頁碼級溯源，讓 AI 檢索結果「可被查核」

每一筆提案都記錄了 `fileName` 與 `page`，使用者查到一則決議後，可以一鍵開啟原始 PDF
並直接翻到指定頁數核對。實測 98 個檔名參照與磁碟上 98 份 PDF **100% 對應**，
零死連結、零大小寫不符（`.pdf` 與 `.PDF` 混用但完全一致，可安全部署於 Linux 主機）。

這一點值得在競賽中重點強調。現在多數 AI 檢索作品的通病就是「答得很流暢但無法驗證」，
而公文與法規領域根本不能接受無法溯源的答案。這個設計直接解決了信任問題。

### 2.2 抽取邏輯正確處理了會議紀錄最容易踩的坑

教務會議紀錄有一個結構陷阱：每份紀錄開頭會先回顧**前次會議**各案的「執行情形」，
之後才列出**本次**提案。若抽取時不加區分，同一個提案會在連續兩份紀錄中被收錄兩次。

我用 98 份 PDF 全文抽取後交叉比對，並逐案人工核對 4 份代表性檔案：

| 檔案 | PDF 中「案由：」總數 | `data.json` 收錄 | 核對結論 |
|------|-------------------:|----------------:|----------|
| `105-1.pdf` | 29 | 5 | 前 24 筆為 104-2 會議之執行情形回顧，**正確排除** |
| `99-2.pdf` | 18 | 7 | 前 11 筆為 99-1 會議之執行情形回顧，**正確排除** |
| `113-1.PDF` | 19 | 2 | 前 17 筆屬 112-4 會議，且已正確收錄於 `112-4.PDF` 之下，**無漏收** |
| `95-3.pdf` | 35 | 16 | 本次提案正確；`提案八` 移至臨時會後改記為`【提案一】（原提案八）`，**編號變動亦有追蹤** |

換句話說，PDF 中 1,851 個「案由：」被正確收斂為 999 筆不重複提案。
最後一列尤其值得一提——連提案在臨時會重新編號的情況都保留了原編號對照，這是人工校對過的痕跡。

> 這一節的驗證過程本身就是很好的參賽素材：它證明資料不是「丟給 AI 跑一遍」的產物。

### 2.3 中文行政文本的正規化處理紮實

四個容易被忽略的細節都處理了：

1. **中文數字年度**：「九十二學年度」正確轉為 92，與「100 學年度」統一為同一維度
2. **CJK 相容字元**：實測有 **12 筆** `meetingName` 的「年」「度」使用 Unicode 相容字
   （U+F98E、U+FA01）而非常用字。程式用 `[年年][度度]` 字元集兼容，
   若沒處理，這 12 筆的年度會全部變成「未知」而從年度篩選中消失
3. **臨時會議排序**：臨時會的 `seq` 給 99，確保排在同學期正式會議之後而非之前
4. **提案序號**：從`【提案一】`抽出數字，讓同一場會議內的提案維持原始議程順序

排序採「年度 → 學期 → 次別 → 提案號」四層，不隨關鍵字改變，
所以同一組查詢條件每次都得到相同順序——對需要引用固定筆數的行政作業很重要。

### 2.4 資安處理完整，無 XSS 破口

- 所有輸出欄位經 `escapeHtml()` 處理 `& < > " '`
- 關鍵字高亮的 regex 先經 `escapeRegExp()`，使用者輸入 `.*` 等符號不會失控
- 彈窗全文使用 `textContent` 而非 `innerHTML`

實測資料中含有各種括號與符號的案由都能安全渲染。這在 vibe coding 作品中並不常見。

### 2.5 技術選型符合單位實況

零框架、零套件、零後端、零編譯。整個系統就是一個 HTML 加一個 JSON，
放到任何靜態網頁空間就能跑，交接時不需要對方懂 npm 或資料庫。

對一個沒有專職資訊人力、承辦可能三年一輪調的行政單位，
「五年後還跑得起來」比「架構漂亮」重要得多。這個判斷是正確的。

### 2.6 AI 助理有成本意識與人工兜底

`indextest.html` 的側欄助理不只是把 chatbot 塞進 iframe：

- iframe 採延遲載入（首次開啟才寫入 `src`），不拖慢首頁
- 剩餘次數標籤會隨用量轉為警示色（≤10）與危險色（≤5）
- 關閉後有 20 秒冷卻並顯示倒數進度條
- 次數用盡時顯示專屬畫面，導引洽教務處分機 62441

「AI 服務要有節流，且用完要有人接手」——這個產品思維比技術實作更值得展示。
（機制本身的漏洞見 3.3。）

### 2.7 行動版體驗處理細緻

1100px 與 768px 兩段斷點。手機版把 AI 側欄從「右側推入」改為「底部展開 70vh」，
浮動按鈕也同步移到側欄上方，避免被遮擋。這類細節通常是被跳過的。

#### 3.3 AI 助理的使用次數上限形同虛設 — ⚠️ 已於 2026-08-11 加固（非完整修復，見下方限制聲明）

```javascript
const MAX_USAGE = 30;
const STORAGE_KEY = "meetmind_usage_v1";
```

原本兩個問題：

1. **計數存在 localStorage**：清除瀏覽資料、換瀏覽器或開無痕視窗即歸零。使用者可無限次使用。
2. **計數單位錯誤**：`openSidebar()` 才扣次數，扣的是「開啟側欄次數」而非「提問次數」。
   開啟一次側欄後可以在裡面問一百個問題，只算 1 次。

**這一項與其他 4 項不同：它沒有「完整修復」，只有「盡力加固」**，原因是這是純前端、
無後端的靜態網頁架構，本質上就無法做到真正可靠的用量控管——不管前端寫得多嚴謹，
使用者只要清除瀏覽資料或開無痕視窗就能繞過，這是架構層級的限制，不是程式碼寫法的問題。

**已完成的加固**（`indextest.html`）：

1. **雙重儲存＋取較小值**：次數同時寫入 localStorage 與 cookie（效期 1 年），
   讀取時取兩者最小值。實測：只清 localStorage、不清 cookie，次數不會回滿
   （cookie 仍保留較低值）。無痕視窗仍會完全繞過，這是任何純前端方案都無法解決的。
2. **單次開啟逾時自動關閉（10 分鐘）**：縮小「開一次側欄、在時效內問無限問題」
   只算 1 次的曝險視窗，但無法完全消除——因為 Copilot Studio 的簡易 iframe 嵌入
   不會把訊息層級的事件回傳給上層頁面（跨網域限制），前端拿不到「使用者問了幾則訊息」
   這個數字，只能拿到「側欄開了多久」。
3. **文案誠實化**：「剩餘 N 次」改為「剩餘 N 次開啟機會」，並在使用次數用盡畫面加註
   「每次開啟可於 10 分鐘內詢問多個問題」，讓使用者與管理端不會誤解為逐訊息計費。

**仍然存在、且無法只靠前端程式碼解決的限制**：若 Copilot Studio 依訊息數計費，
唯一可靠的做法是在伺服器端（Power Automate、Azure Function，
或 Copilot Studio 頻道本身的訊息上限設定）驗證，這需要存取 Power Platform 後台，
不在這次能處理的範圍內，已在程式碼註解中明確聲明此限制。

#### 3.4 Copilot Studio 端點與環境 ID 硬編碼在前端 — ⚠️ 已於 2026-08-11 加固（無法完全修復，見說明）

`indextest.html` 第 637 行：

```
https://copilotstudio.microsoft.com/environments/Default-{環境GUID}/bots/{機器人名稱}/webchat?__version__=2
```

環境 GUID 與機器人名稱寫在 HTML 屬性裡，任何人檢視原始碼即可取得。
**這一點本質上無法用程式碼修復**：iframe 要嵌入這個 webchat，網址就必須送到瀏覽器端，
只要瀏覽器拿得到，使用者就拿得到，不管把網址藏在哪一行程式碼都一樣。

**已完成的加固**：原本 iframe 沒有 `sandbox` 屬性、也沒有 `referrerpolicy`，現已加上：

```html
sandbox="allow-scripts allow-same-origin allow-forms allow-popups allow-popups-to-escape-sandbox"
referrerpolicy="no-referrer"
```

- `sandbox` 限制 iframe 只保留 webchat 運作實際需要的權限，刻意不開放
  `allow-top-navigation`（不能整頁跳轉劫持使用者）、`allow-modals`（不能跳原生對話框）、
  `allow-downloads`（不能觸發檔案下載）
- `referrerpolicy="no-referrer"` 避免把本頁網址透露給 Microsoft 網域
- 保留 `allow-same-origin` 是刻意的取捨：拿掉會讓聊天元件無法用自己的儲存機制
  維持對話狀態，可能直接讓助理壞掉；在沒有存取即時 Copilot Studio 實體驗證的前提下，
  選擇不冒這個風險

**做不到、需要你到 Power Platform 後台處理的部分**：真正的存取控制
（僅限校內網域、需要登入才能對話）必須在 Copilot Studio／Power Platform 的頻道安全性設定裡做，
這是我沒有存取權限、也無法透過修改這兩支 HTML 檔案達成的部分。

#### 3.9 搜尋結果無法分享，也無法匯出 — ✅ 已於 2026-08-11 修復

原本沒有 URL 查詢參數，查到關鍵決議後無法把連結貼給同事，

**已實作**：

1. **URL 分享狀態**：新增 `syncUrlState()`／`loadUrlState()`，關鍵字、年度、類型、排序方式
   同步寫入 URL query string（用 `replaceState` 而非 `pushState`，避免每敲一個字就塞爆
   瀏覽器歷史紀錄）；開啟含參數的連結會自動還原搜尋條件並立即執行搜尋。
   驗證：`?q=學則+修正&year=113` 開啟後正確還原輸入框與年度篩選，顯示 2 筆結果。
2. **CSV 匯出**：新增「匯出目前結果為 CSV」按鈕，匯出**目前篩選後的全部結果**
   （非僅當前頁），欄位為年度／會議／單位／案由／內容／決議／頁碼／PDF 相對路徑；
   加上 UTF-8 BOM 確保 Excel 開啟中文不亂碼；正確處理欄位內含逗號、引號、換行的
   CSV 逸出。驗證：實際下載內容經瀏覽器層級攔截確認欄位與 BOM 皆正確；
   無結果時改跳出提示，不會產生空白檔案。

#### 3.10 兩份檔案各複製一份邏輯，且無版本控管

#### 3.15 無障礙缺口

- 搜尋結果筆數變化未用 `aria-live` 播報，螢幕閱讀器使用者不知道結果已更新
- 表頭缺少 `scope="col"`

大專院校網站有無障礙規範要求，這幾項改動不大但影響評分。

## 五、競賽敘事建議

目前作品的呈現方式是「一個搜尋系統 + 一個 chatbot」，這會嚴重低估你實際完成的工作。
建議改成以下敘事：

> **用 Gemini AI 把 23 年、102 場教務會議、983 筆決議變成可稽核的機構記憶。**
> 每一個查詢結果都能追到原始 PDF 的第幾頁——AI 給的答案，人可以驗證。

四個可以拿出來講的硬證據：

1. **AI 抽取管線本身**：獨立的兩階段 Gemini 解析架構（定位討論區段 → 欄位結構化），
   而非隨手丟給 AI 跑一次——完整說明見 [EXTRACTION.md](EXTRACTION.md)
2. **資料規模與品質**：983 筆 × 8 欄位零空值、98 個 PDF 連結零死鏈、ID 零重複
3. **抽取正確性**：PDF 中 1,851 個「案由：」正確收斂為 999 筆不重複提案（後於 2026-08-11 再去除 95 學年度 16 筆重複紀錄，現為 983 筆），
   自動排除「前次會議決議執行情形」的重複段落（附 2.2 節的 4 份逐案核對表）
4. **中文公文的工程細節**：中文數字年度轉換、12 筆 CJK 相容字元兼容、
   臨時會議時序權重、提案改編號追蹤

第 4 點特別值得展開。「處理 Unicode 相容字元讓 12 筆資料不會消失」這種細節，
比任何架構圖都更能證明作品是真的做過、而不是產生出來的。

還有一個值得講的角度：**這次分析不只驗證了 AI 抽取的結果，還抓出了原抽取工具「雙鍵去重」機制的一個系統性盲點**
（標題被改寫時去重會失效，見 [EXTRACTION.md](EXTRACTION.md) 第三節）——這說明整個系統經過了不只一層的品質把關，
不是做完就上架，而是有回頭檢查、有抓到問題、有修復紀錄的完整迭代過程。
